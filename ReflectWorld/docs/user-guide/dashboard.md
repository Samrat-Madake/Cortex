# Dashboard Guide

> The ReflectWorld Dashboard is the main interface for seeing what cameras saw,
> what the system remembered, and how to interact with that state.
>
> The default URL is `http://localhost:3210`. Change the port with `PORT` or
> `--port`. For the runtime shape, see the
> [architecture overview](../architecture/overview.md). For HTTP endpoints, see
> [reference/http-api.md](../reference/http-api.md).

---

## TL;DR

| Area | What you do |
|---|---|
| **Source management and Live View** | Add, stop, and remove video sources; watch RTSP or camera streams live |
| **Segment timeline** | Browse analyzed video segments, summaries, and safety levels |
| **Entity and Sightings panels** | Inspect recognized people or objects and their previous appearances |
| **Semantic Memory** | Inspect the long-term scene profile, known entities, and routines |
| **Chat** | Ask natural-language questions about current observations and memory |
| **Settings** | Adjust runtime perception level, capture mode, and sampling rate |

---

## 1. Source Management and Live View

A source is a ReflectWorld input: either an uploaded video file or a live stream.

### Add a Source

- **Upload a local video**: upload an `.mp4`, select it, and start analysis.
  Uploaded files are handled as `local_file` inputs with PTS time, EOF drain,
  and backpressure. Long videos do not grow memory unbounded.
- **Add a live stream**: enter a URL and a name. RTSP, USB cameras, phone
  streams, and HTTP streams are routed through go2rtc and handled as
  `live_stream` inputs.

Example:

```text
rtsp://user:pass@192.168.1.10:554/stream
```

In multi-user mode, per-session source limits apply.

Adding a live source makes the backend connect to an external address. In a
local trusted environment this is convenient. In public deployments, source
URLs are an SSRF and local-file-read boundary; enable authentication and source
validation as described in [configuration.md](./configuration.md).

### Live View

Live sources can be previewed directly in the Dashboard. The Dashboard proxies
go2rtc through the same origin, avoiding browser cross-origin issues. Playback
uses fragmented MP4, MJPEG, or single-frame JPEG depending on browser support
and source state.

### Stop, Remove, and Clear

- **Stop**: stops analysis for the source but keeps its data and history.
- **Remove**: stops and removes the source instance and scoped runtime state.
  Removing a source **does not delete the uploaded original video file**.
- **Clear**: removes uploaded videos and analysis data visible in the Dashboard.
  In multi-user mode, non-admin users can only clear their own session data.

## 2. Segment Timeline

Each analyzed video segment becomes a **segment card** in the timeline. A card
contains:

- **Short Summary** generated by the VLM.
- **Safety Level** and risk decision.
- **Targets and entities** seen in the segment. With Level 1, these include
  detection and ReID-backed identity continuity.
- **Keyframe thumbnail**. Open a segment for details and clip playback.

Cards update progressively. A text summary may arrive first, while safety and
entity fields are filled in later.

The timeline focuses on active and recent analysis. For wider history, use chat
or `GET /api/segments/recent`.

---

## 3. Entity and Sightings Panels

An **entity** is a view that groups what appears to be the same person or object
across segments and time.

- **Entity card**: representative image, identifier, and resolved name if known.
- **Sightings**: thumbnails and timestamps for previous appearances.
- **Identity continuity**: with Level 1, ArcFace-based face ReID links the same
  person across segments. With Level 0, entities are mainly VLM-described
  subjects, so cross-segment continuity is limited.

Identity is modeled as evidence plus decision. Detection and ReID produce
evidence vectors; the runtime resolves identity state when confidence is
sufficient. See the [architecture overview](../architecture/overview.md).

---

## 4. Semantic Memory

As a camera is analyzed over time, ReflectWorld builds a **Semantic Context** for
that camera:

- scene description,
- known entities,
- daily routines,
- anomaly baseline.

This comes from the memory system, which organizes memories by time scale and
abstraction level. It gives chat and notifications long-term context instead of
only the latest segment. See the
[architecture overview](../architecture/overview.md).

## 5. Chat

Open the chat panel from the lower-right button and ask questions such as:

- "Who was that person? Have they appeared before?"
- "Was anything unusual in the last ten minutes?"
- "Who came to the front door today?"

Chat uses the current Dashboard context, optionally scoped to a `camera_id`,
retrieves memory, and calls the configured text LLM, `LLM_MODEL`. It supports
streaming output and keeps a small conversation history, currently about eight
turns.

Chat is cost-bearing because each request calls an LLM. Local single-user mode
is open by default; public deployments should enable multi-user authentication
and per-session rate limits.

## 6. Settings

Settings are the small set of options that can change at runtime and take
effect immediately. They affect how ReflectWorld captures and how deeply it
analyzes, not deployment-time provider configuration.

| Setting | Values | Default | Meaning |
|---|---|---|---|
| **`vlm_model`** | `auto` or a listed vision model | `auto` | Runtime model preference for Dashboard-triggered analysis. Provider credentials still come from deployment configuration. |
| **`analysis_level`** | `auto` / `0` / `1` / `2` | `auto` | Perception depth. `0` is VLM-only; `1` enables local detection and ReID when Level 1 is installed; `2` is reserved for higher-level modes not included in the first public release. |
| **`audio_model`** | `moonshine-tiny` / `none` | `moonshine-tiny` | Runtime audio/STT preference shown by the Dashboard. Some audio runtime changes may require restart depending on deployment. |
| **`capture_mode`** | `stream` / `event` / `snapshot` | `stream` | Capture strategy. |
| **`sampling_rate`** | greater than `0`, up to `30` | `1` | Frame sampling rate in fps. Higher values are more detailed but more expensive and slower. |

Changes go through `POST /api/config` and apply immediately to the running
Dashboard session.

Distinguish these runtime settings from deployment-time configuration:

- Runtime settings are changed in the Dashboard.
- Provider, API key, embedder, port, and multi-user settings live in
  `.env` for standalone mode or `configure` for plugin mode and require restart.

## 7. Multi-User Mode Differences

The default is local single-user mode. All features are open.

When `DASHBOARD_MULTI_USER=true` is enabled for public demos or shared
deployments:

- users enter through a Dashboard session with `session_id` and `user_id`,
- source and memory visibility is scoped to the session,
- mutation, chat, and proxy operations require a valid session,
- quotas control active sessions, source count, and session TTL.

See [configuration.md](./configuration.md) for when to enable multi-user mode
and how quotas work.
